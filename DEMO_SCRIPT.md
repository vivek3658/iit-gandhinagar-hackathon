# Three-minute demo script

**Presenter:** team lead
**Target length:** 3:00
**Demo rule:** use a dedicated test account and clearly call out estimated or self-reported values. Do not show personal account data or imply that a demo value is live/verified unless you have checked its source.

| Time | Show | Narration |
|---|---|---|
| 0:00–0:15 | App opening screen | “We are building URJA Vatika for GEDA’s Mission LiFE challenge. The goal is to make sustainable choices easier to understand and repeat—not just show a one-time carbon number.” |
| 0:15–0:40 | Sign-in and profile/dashboard | “A citizen signs in and provides household context. That gives the prototype inputs for a more relevant starting point. The app does not silently inspect appliances or utility accounts.” |
| 0:40–1:05 | Footprint/impact summary | “Here the app turns entered information into an estimated footprint and practical suggestions. These numbers are estimates from the inputs and code-defined factors, not live meter readings or independently verified savings.” |
| 1:05–1:35 | Daily quest or action card, then activity feed | “The next step is a small action. A user confirms completion, earns in-app progress, and can review activity in the feed. A confirmation is self-reported; points are engagement, not carbon credits.” |
| 1:35–2:00 | Learning and waste-sorting round | “The learning area pairs short lessons with a sorting game. A round can use up to fifteen items, so the interaction stays quick enough to repeat.” |
| 2:00–2:25 | Garden and mascot interaction | “Progress also has a visual home: the garden and mascot make participation feel personal. This is game progression—it is not evidence that a specific quantity of emissions was avoided.” |
| 2:25–2:45 | Community/leaderboard view, if populated | “Community features can compare participation using the data available to the configured backend. If the demo environment is empty, we will show the feature without presenting sample values as real community results.” |
| 2:45–3:00 | Return to dashboard or closing slide | “Our next validation step is stronger data provenance: opt-in real utility integrations, an auditable impact method, and deployment-level testing. Today we are presenting a working engagement prototype and being explicit about what remains to be verified.” |

## Rehearsal checklist

- Pre-check the test account, API reachability, and screen navigation; keep a fallback recording if sign-in or the demo environment is unavailable.
- Use only demo-account data. Never invent users, district totals, savings, or benchmark results to fill an empty view.
- If an integration fails, explain that the view depends on the configured backend and continue with the local learning/game flow.
- Keep “estimated,” “self-reported,” and “not yet verified” visible in narration wherever they apply.
