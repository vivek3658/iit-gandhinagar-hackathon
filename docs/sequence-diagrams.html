Flow 1: Citizen Onboarding & Baseline Footprint Calibration

Citizen signs up, provides household energy profiles (DISCOM consumer number, AC count, monthly power bill), calculates baseline carbon footprint against Gujarat benchmarks, and initializes their mascot companion (Chirpy or Chiku). 

sequenceDiagram
    autonumber
    actor Citizen as Citizen (Mobile/Web)
    participant Fastify as Fastify Router & TypeBox
    participant AuthCtrl as auth.controller
    participant FootprintSrv as footprint.service
    participant MascotSrv as mascot.service
    participant GardenSrv as garden.service
    participant DB as PostgreSQL DB
    participant Cache as Redis 7 Cache

    Citizen->>Fastify: POST /api/v1/auth/register
{email, phone, discom, bill_inr, appliances}
    Fastify->>Fastify: Validate schema with TypeBox
    Fastify->>AuthCtrl: register(request, reply)
    AuthCtrl->>DB: Hash password (argon2) & insert Citizen User
    DB-->>AuthCtrl: User Record Created (UUID)
    
    AuthCtrl->>FootprintSrv: calculateBaseline(userId, bill_inr, appliances)
    Note over FootprintSrv: Applies Gujarat CEA Grid Emission Factor
(0.82 kg CO2 / kWh) & Tariffs
    FootprintSrv->>DB: Save BaselineFootprintRecord
    
    AuthCtrl->>MascotSrv: initializeMascot(userId, "sparrow" | "squirrel")
    MascotSrv->>DB: Insert MascotState (mood=100, seeds=50)
    MascotSrv->>Cache: Set mascot:state:{userId} in Redis
    
    AuthCtrl->>GardenSrv: initializeGarden(userId)
    GardenSrv->>DB: Provision 3x3 Plot Matrix (Plot #0: "Sprout")
    
    AuthCtrl->>Citizen: 201 Created + JWT Access Token
{user, baseline_co2, mascot, initial_plot}
⚡ Fastify Schema Isolation

Body validation uses strict TypeBox schema; invalid fields or malformed appliance counts are rejected with HTTP 400 before hitting services.

🌿 Seed Provisioning

Onboarding awards the citizen's mascot 50 eco-seeds and activates the first plot in their digital Urja Vatika garden.

Flow 2: Micro-Task Verification & Forest Garden Growth Loop

Citizen completes a daily Mission LiFE micro-task (e.g. setting AC to 24°C, switching off TV standby, morning solar shift). The backend validates the action, rewards eco-points, feeds the mascot, and blooms the forest garden plot. 

sequenceDiagram
    autonumber
    actor Citizen as Citizen (Mobile App)
    participant Fastify as Fastify (app.inject/live)
    participant TaskCtrl as tasks.controller
    participant TaskSrv as tasks.service
    participant MascotSrv as mascot.service
    participant GardenSrv as garden.service
    participant Redis as Redis Cache & PubSub
    participant DB as PostgreSQL DB

    Citizen->>Fastify: POST /api/v1/tasks/complete
Bearer JWT {taskId: "AC_24_DEGREE", proofData}
    Fastify->>TaskCtrl: verifyAuth & routeHandler
    TaskCtrl->>TaskSrv: recordCompletion(userId, taskId)
    TaskSrv->>DB: Check daily duplicate & insert TaskCompletion
    TaskSrv-->>TaskCtrl: Award: 30 Eco-Seeds, 1.2 kWh Saved

    par Sync Mascot Mood
        TaskCtrl->>MascotSrv: feedMascot(userId, seeds=30)
        MascotSrv->>Redis: HINCRBY mascot:{userId} mood 15
        MascotSrv->>Redis: HINCRBY mascot:{userId} seeds 30
    and Advance Urja Garden Bloom
        TaskCtrl->>GardenSrv: waterActivePlot(userId, plotId=0)
        GardenSrv->>Redis: HSET garden:{userId}:plot:0 stage "Blooming Neem"
        GardenSrv->>DB: Update GardenPlot stage & hydration
    and Update District Leaderboard
        TaskCtrl->>Redis: ZINCRBY leaderboard:district:ahmedabad 30 userId
    end

    TaskCtrl->>Citizen: 200 OK {success: true, new_stage: "Blooming Neem", mascot_dialogue: "Chirpy chirped happily!"}
🚀 Parallel Pipeline Execution

Mascot mood updates, garden plot blooming, and leaderboard increment run concurrently via Promise.all() for minimum latency (<15ms).

🐦 Interactive Mascot Reaction

The response includes localized celebratory dialogue from Chirpy or Chiku in Gujarati/Hindi/English.

Flow 3: Gujarat DISCOM Peak Grid Hour Demand Response Nudge

Gujarat DISCOM (e.g. UGVCL/DGVCL) triggers an impending peak load alert. The backend broadcasts geo-targeted nudges, citizens commit to 1-hour appliance throttling, and the grid demand response is aggregated for GEDA administrators. 

sequenceDiagram
    autonumber
    actor DISCOM as Gujarat DISCOM / SLDC Webhook
    participant NudgeCtrl as nudges.controller
    participant NudgeSrv as nudges.service
    participant Queue as BullMQ Worker Queue
    participant FCM as Push Notification Service
    actor Citizen as 100,000+ Citizens (Ahmedabad/Surat)
    participant Redis as Redis Pub/Sub

    DISCOM->>NudgeCtrl: POST /api/v1/nudges/discom-alert
X-Signature-Auth {circle: "UGVCL", peak: "18:30-21:30", target_mw: 50}
    NudgeCtrl->>NudgeSrv: validateAndScheduleAlert(payload)
    NudgeSrv->>Redis: SETEX active_peak:UGVCL 10800 {status: "PEAK"}
    NudgeSrv->>Queue: Enqueue BroadcastJob(circle: "UGVCL", urgency: "HIGH")
    NudgeCtrl-->>DISCOM: 202 Accepted {broadcast_job_id: "job_94812"}

    Note over Queue,FCM: BullMQ Worker batch partitions 100k citizens into 500-user chunks
    Queue->>FCM: Send Batch Push ("Peak Grid Alert: Help Chirpy protect Gujarat Grid!")
    FCM->>Citizen: Notification: "Turn off 1 heavy appliance now for 3x Solar Acorns"

    Citizen->>NudgeCtrl: POST /api/v1/nudges/commit
{alertId, commitment: "OFF_GEYSER_AC"}
    NudgeCtrl->>Redis: HINCRBY grid_response:UGVCL committed_users 1
    NudgeCtrl->>Citizen: 200 OK {multiplier: 3, mascot_shield_active: true}
⚡ 50,000 req/sec Surge Protection

Citizen commitments increment a Redis atomic counter (HINCRBY) rather than hitting relational table row locks.

🛡️ Mascot Shield Mechanic

Committing to peak demand protection grants the citizen's garden a "Drought Shield", preventing wilting during peak power surges.

Flow 5: High-Concurrency Ward & District Leaderboards

Shows how millions of citizen eco-point updates are ingested without DB table locks, leveraging Redis Sorted Sets for sub-millisecond leaderboard retrieval across Gujarat districts. 

sequenceDiagram
    autonumber
    actor Citizen as Citizen / Ward Resident
    participant Fastify as Fastify Router
    participant LeaderCtrl as leaderboard.controller
    participant LeaderSrv as leaderboard.service
    participant Redis as Redis 7 (ZSET Engine)
    participant DB as PostgreSQL (Read-Replica)

    Citizen->>Fastify: GET /api/v1/leaderboard/district?district=Ahmedabad&range=1-10
    Fastify->>LeaderCtrl: getDistrictLeaderboard(request, reply)
    LeaderCtrl->>LeaderSrv: fetchTopRankings("Ahmedabad", 0, 9)
    
    LeaderSrv->>Redis: ZREVRANGE leaderboard:district:Ahmedabad 0 9 WITHSCORES
    Redis-->>LeaderSrv: Top 10 User IDs + Eco-Points in 0.8ms
    
    LeaderSrv->>Redis: MGET user:names:{id1, id2, ...} (Hydration Cache)
    alt Cache Miss on Names
        LeaderSrv->>DB: SELECT id, name, mascot_skin FROM users WHERE id IN (...)
        DB-->>LeaderSrv: Profile Metadata
    end
    
    LeaderSrv->>Redis: ZREVRANK leaderboard:district:Ahmedabad {currentUserId}
    Redis-->>LeaderSrv: Citizen Rank: 42
    
    LeaderSrv-->>LeaderCtrl: Composite Leaderboard View
    LeaderCtrl->>Citizen: 200 OK {district: "Ahmedabad", rank: 42, top_10: [...]}
⚡ O(log N) Time Complexity

Redis Sorted Sets (ZREVRANGE) allow 500,000 concurrent citizens to check real-time rank with near-zero latency.

🛡️ Zero DB Overload

PostgreSQL is shielded by Redis profile hydration cache, ensuring no queries are executed on the primary database for rank reads.
